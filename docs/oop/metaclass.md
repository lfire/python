# 第 045 讲 · 元类：__new__、type 与类创建过程

> 元类控制的是「类如何被创建」，而不是实例如何被创建；绝大多数需求用类装饰器或 __init_subclass__ 就能更清楚地解决。本讲的目标是「能读懂并写出框架级的类定制逻辑」。先建立直觉，再用可运行代码把规则固定下来，最后放进工程场景里看边界与代价；全程建议边读边改参数、边猜输出。

### 2.1 主示例

**类也是对象**。这里的关键词是「什么时候」和「代价是什么」。Python 的机制大多不是非黑即白的开关，而是在可读性、性能与灵活性之间做的取舍。把取舍写清楚，遇到新版本或新框架时才能自己推导，而不是重新背一遍结论。

```python
class Validated:
    def __init_subclass__(cls, *, table=None, **kw):
        super().__init_subclass__(**kw)
        cls.table = table or cls.__name__.lower()

class Order(Validated, table="orders"): pass
print(Order.table)
```

### 2.2 对照写法

```python
def add_repr(cls):
    cls.__repr__ = lambda self: f"<{type(self).__name__}>"
    return cls

@add_repr
class Item: pass
print(Item())
```

## 3. 深入一步：规则与边界

**__new__ 与 __init__ 分工**。工程里最容易出问题的不是不会用，而是用在错误的边界上：数据规模变大、并发进入、依赖升级、跨平台部署之后，原本成立的假设会逐个失效。因此本讲同时给出适用条件、失效信号和一条可回退的路径。

**__init_subclass__**。建议把它和相邻知识点连成一条线：输入是什么、状态存在哪里、失败时谁负责收尾。这三问能覆盖绝大多数线上问题，也是后续阶段反复使用的分析框架；能回答这三问，才算真正掌握而不是记住了 API 名字。

## 4. 工程实践

ORM 映射、字段注册、接口校验是元类的经典场景；写之前先确认没有更轻的方案 **元类冲突**。建议把它和相邻知识点连成一条线：输入是什么、状态存在哪里、失败时谁负责收尾。这三问能覆盖绝大多数线上问题，也是后续阶段反复使用的分析框架；能回答这三问，才算真正掌握而不是记住了 API 名字。 落地时把这条结论写进检查表或自动化测试，避免只停留在口头约定。
