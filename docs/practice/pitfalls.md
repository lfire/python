### 导学 · 建立地图

- **001 开篇：Python 是什么，为什么值得学**：把 Python 当成慢一点的 C 来写，会丢掉它最大的优势：它真正的定位是胶水语言与工程效率放大器
- **002 环境与工具链：解释器、虚拟环境与编辑器**：全局 pip install 会让两个项目互相污染，且最终无法说清生产环境到底装了什么
- **003 第一行 Python：从源码到字节码再到执行**：以为改了 .py 一定会重新执行，却忽略了导入缓存与 pyc 时间戳，是调试时最常见的错觉
- **004 工具链全景：写代码、查问题、验质量**：只靠 print 调试，遇到异步或生成器问题会失去上下文；pdb 与 logging 才是可复用的手段
- **005 学习路线：十三个阶段如何递进**：跳过对象模型直接学框架，遇到描述符、元类、GIL 时只能死记结论，无法自己推导

### 阶段一 · 编程地基

- **006 一切皆对象：id、type、value 与可变性**：用 is 比较值、用 == 比较身份是最典型的误用；is 只该用来判断 None、True、False 这类单例
- **007 变量是名字绑定：赋值、引用与命名规范**：把可变对象当默认参数、或在循环里复用同一个 list，会产生跨调用/跨迭代的幽灵状态
- **008 数值体系：int 任意精度、float、Decimal 与 bool**：金额用 float 累加、或用 == 判断两个计算结果相等，是财务系统最典型的线上事故
- **009 字符串与编码：Unicode、str / bytes 与转义**：用 str 去拼接 bytes、或用系统默认编码打开文件，会在跨平台时突然乱码
- **010 字符串操作：切片、f-string 与常用方法**：切片越界不报错、步长为负时边界含义变化，是文本处理里最容易写错的地方
- **011 运算符与表达式：优先级、短路与真值**：用 or 给可能为 0 或空容器的值兜底，会把合法的假值悄悄替换掉，应显式判断 is None
- **012 分支：if / elif / else 与 match-case**：把十几层 if 叠在一起，既难测又容易漏分支；模式匹配与字典分派能让分支结构显式化
- **013 循环：for / while、range 与循环 else**：在遍历 list 的同时删除元素会跳项，应遍历副本或用列表推导式重建
- **014 输入输出与文件初识：print、input、open、with**：不指定 encoding 的 open 依赖平台默认编码，同一份代码在 Windows 与 Linux 上可能读出不同结果
- **015 异常：捕获、异常链与自定义异常**：用裸 except 或 except Exception 吞掉一切，会把键盘中断与编程错误一起藏起来，排障时只剩一个沉默的系统
- **016 阶段综合：交互式命令行计算器**：用 eval 直接执行用户输入的表达式等于把解释器交给用户，是典型的命令注入入口

### 阶段二 · 容器与序列

- **017 序列协议与通用操作**：把切片得到的副本当成原对象的视图，改了半天发现没生效，是初学者最常见的误会
- **018 list：动态数组、操作与时间复杂度**：在列表头部反复 insert(0, x) 会搬移整个数组，数据量大时比 deque 慢几个数量级
- **019 list 进阶：切片赋值、排序与常见陷阱**：用 [[0]*3]*3 创建二维列表会得到三个指向同一行的引用，改一格变成改一行
- **020 tuple 与具名元组：不可变性的价值**：把坐标、配置项、数据库一行记录都塞进只带下标的元组，读代码的人必须数位置
- **021 dict：哈希表、视图与插入顺序**：用可变对象做键、或假设哈希值永不变化，会让查找静默失败；自定义 __eq__ 必须同步 __hash__
- **022 dict 进阶：默认字典、计数器与合并**：defaultdict 在嵌套层级深时会悄悄创建不存在的键，读路径也可能污染数据
- **023 set / frozenset：哈希、集合运算与去重**：对 list 反复用 in 判重会让整体复杂度变成 O(n²)，数据一上来就卡死
- **024 推导式：四种写法与可读性边界**：嵌套三层以上还硬塞推导式，可读性会急转直下，此时普通循环配合早返回更清楚
- **025 迭代协议：iterable、iterator 与惰性求值**：把迭代器当列表用（先 len 再遍历、或遍历两次），第二次会拿到空结果，且不会报错
- **026 生成器与 yield：send / throw / close**：忘记 close() 会让持有文件句柄的生成器迟迟不释放；在 finally 里写清理逻辑才可靠
- **027 阶段综合：词频统计与内存版 KV**：一次性把所有行读进 list 做统计，文件一大就 OOM；应逐行迭代、增量累计

### 阶段三 · 函数与抽象

- **028 函数定义与参数形态**：默认值在函数定义时求值一次，若默认是可变对象，所有调用会共享同一份状态
- **029 返回值、None 与多返回值**：用返回 None 表示失败、又用 None 表示合法结果，会让调用方无法区分两种情况
- **030 作用域、LEGB 与闭包延迟绑定**：在循环里定义 lambda 直接引用循环变量，会得到一批行为完全相同的函数，且没有任何报错
- **031 高阶函数、lambda 与 map / filter / reduce**：为了炫技写长 lambda，可调试性与可读性都会变差；命名函数配合推导式往往更好
- **032 装饰器原理与 functools.wraps**：不写 wraps 会让所有被装饰函数都叫 wrapper，日志、文档生成、依赖注入与调试全部失真
- **033 带参装饰器、叠加顺序与类装饰器**：带参装饰器少写一层返回值，会得到「缺少参数」这类看似无关的报错
- **034 偏函数、可调用对象与函数式工具**：给含可变参数或带副作用的函数加 lru_cache，会得到跨调用串数据甚至安全问题
- **035 模块与包：import 机制与循环导入**：把可执行逻辑写在模块顶层，会在「只是导入一下」时触发副作用；循环导入也随之而来
- **036 类型注解、typing 与渐进式类型**：用 Any 到处灭火，等于把检查器关掉；类型注解与运行时校验（pydantic）是两件事，不要互相代替
- **037 阶段综合：缓存装饰器库与插件注册表**：装饰器里用全局字典缓存而不加锁，多线程下会出现重复计算与状态竞争

### 阶段四 · 面向对象与元编程

- **038 类与实例：__init__、self 与属性**：把所有状态都放类属性，多个实例会共享同一份可变数据，改一个实例影响全部
- **039 属性查找、MRO 与 super**：混用 super() 与显式父类调用，会让某个初始化方法被执行两次或完全跳过
- **040 访问控制、property 与描述符协议**：把校验写在 __init__ 里，后续赋值就绕过了校验；数据描述符才能保证每次赋值都经过同一入口
- **041 特殊方法：repr、比较、算术与容器协议**：定义了 __eq__ 却忘记 __hash__，对象立刻不能进 set 或做 dict 键
- **042 上下文管理器与 with 协议**：在 __exit__ 里随手返回 True，会把真正的错误吞掉，日志里什么线索都不留
- **043 __slots__、弱引用与对象内存布局**：给基类忘了加 __slots__，子类依然带 __dict__，优化等于没做；多继承时槽还可能冲突
- **044 鸭子类型、抽象基类与 Protocol**：为了「规范」给所有内部类型套一层抽象基类，只会增加层次而不增加约束
- **045 元类：__new__、type 与类创建过程**：在元类里做重逻辑会让 IDE、类型检查器与调试器全部失去线索
- **046 反射与自省：getattr、inspect 与 __dict__**：对用户传入的字符串直接 getattr 并调用，等于开了一个任意方法执行入口
- **047 dataclass、attrs 与 pydantic 模型**：把外部输入直接交给 dataclass，类型注解不会拦住任何脏数据，错误会推迟到业务深处才爆
- **048 阶段综合：最小 ORM 与校验框架**：用字符串拼接 SQL 会把注入漏洞写进框架，参数化查询必须在一开始就设计进去

### 阶段五 · 核心机制与运行时

- **049 CPython 编译流程：AST 到字节码**：把 ast.literal_eval 写成 eval，或在编译期优化里改坏行号信息，会让调试栈失去意义
- **050 字节码、栈式虚拟机与 dis 实战**：拿某一版本的字节码当语言规范，升级解释器后结论可能失效
- **051 帧、调用栈与命名空间**：在帧里修改 locals() 字典期待改变局部变量，在多数实现里不会生效
- **052 对象内存布局、引用计数与小对象池**：用 sys.getsizeof 只看对象本身，容器里元素、字符串内容、字典哈希表的开销都算不到
- **053 分代 GC、循环引用与 weakref**：定义了 __del__ 的对象参与循环时旧版本无法回收；缓存里用普通 dict 持有对象会让它们永远活着
- **054 GIL 真相：存在原因、切换与影响边界**：以为有 GIL 就不用加锁，会在复合操作上写出竞态；把 CPU 密集逻辑塞进线程只会更慢
- **055 导入系统源码级：finder、loader 与缓存**：在包 __init__ 里反向导入子模块，很容易撞上半初始化状态，报出看似无关的 AttributeError
- **056 属性访问链路与 __getattribute__**：在 __getattribute__ 里用 self.x 取属性会无限递归，必须用 object.__getattribute__
- **057 可变性、深浅拷贝与共享状态**：把内部可变结构直接返回给调用方，对方一改就等于改了你的私有状态
- **058 性能剖析：timeit、cProfile 与 tracemalloc**：缓存命中、JIT、磁盘预读都会让单次计时失真，凭一次运行下结论常常优化错地方
- **059 阶段综合：简易性能分析器与内存哨兵**：在多线程程序里用全局 profile 回调，会把别的线程事件也算进当前调用树

### 阶段六 · 并发与异步

- **060 并发、并行与 IO 模型全景**：把 IO 密集服务写成多进程，会用大量内存换来并不需要的隔离；反过来则被 GIL 卡住吞吐
- **061 threading：线程生命周期与共享状态**：子线程里抛出的异常不会传到主线程，任务静默失败，日志里却什么都没有
- **062 线程同步：Lock、Condition、Semaphore、Event**：用 RLock 掩盖设计问题、或在持锁时调用外部回调，是死锁最常见的两个来源
- **063 线程池与 Future 模式**：无上限地 submit 会把待办全堆进内存，服务在流量峰值先被自己的队列压垮
- **064 multiprocessing：进程、Pool 与共享内存**：在 spawn 平台把不可 pickle 的对象（lambda、打开的连接）传给子进程，会在启动时报莫名其妙的错误
- **065 进程间通信：Queue、Pipe 与信号**：只靠 kill 强杀进程，队列里未确认的消息会永久丢失或重复处理
- **066 IO 多路复用：select / poll / epoll**：边缘触发模式下没一次性读完缓冲区，事件不会再来，连接会永久卡住
- **067 生成器协程：send、yield from 与调度器**：在生成器里混用 return value 与 yield，容易搞不清 StopIteration.value 到底从哪来
- **068 async / await 与协程对象**：在协程里调用 time.sleep 或同步 requests 会阻塞整个事件循环，一个慢请求拖垮所有并发
- **069 asyncio 深入：Task、Future 与事件循环**：用裸 create_task 不保存引用，任务可能被 GC 回收，异常也永远没人读取
- **070 阶段综合：并发爬虫四级演进**：不做限速与 robots 约束，压垮对方站点同时也让自己被封；分布式化后还会有重复抓取问题

### 阶段七 · 工程化与质量

- **071 项目结构与 src 布局**：把测试放在包内一起发布，或用隐式相对导入，都会让安装后的行为与本地不一致
- **072 依赖管理：venv、uv、锁文件与可复现构建**：开发与生产共用一份无锁依赖，某天上游发版就会让线上行为悄悄变化
- **073 代码规范：PEP 8、ruff、black 与 pre-commit**：一次性对老仓库开全量规则，会产生上万行无关改动，掩盖真正的逻辑变更
- **074 静态检查：mypy / pyright 与渐进式类型**：为赶进度满仓 # type: ignore，等于把检查器变成装饰；技术债会集中在最难查的地方
- **075 单元测试：pytest、fixture 与参数化**：过度 mock 会把测试写成实现的镜像，重构时全部重写，却没验证任何外部行为
- **076 Mock 与测试替身：时间、网络与随机**：mock 了不存在的方法，测试依然会通过，直到真实接口变化才发现
- **077 属性测试、基准测试与模糊测试**：只测正常输入，等于没测编码、空值、极值、Unicode 与超长字符串这些真实事故来源
- **078 日志：logging、结构化日志与追踪关联**：在循环里打 INFO、把密钥或身份证写进日志，既压垮磁盘又制造合规事故
- **079 配置管理：环境变量、.env 与配置中心**：把密钥硬编码或提交进仓库，轮换时只能全量改代码重新发版
- **080 打包与发布：pyproject、wheel 与 PyPI**：把测试数据、本地路径、开发依赖打进 wheel，会让包体积膨胀甚至泄漏内部文件
- **081 阶段综合：把脚本重构成可发布包**：先重构完再补测试，改动面太大时无法判断行为是否保持，重构很容易变成重写

### 阶段八 · 服务端与数据

- **082 HTTP 协议与 WSGI / ASGI**：在 ASGI 应用里直接调用同步阻塞库，会占住事件循环的工作线程
- **083 FastAPI / Flask / Django 选型**：微服务里硬套 Django 的整套 ORM 与 admin，会背上用不到的启动与依赖成本
- **084 路由、依赖注入与请求校验**：把业务逻辑堆在路由函数里，接口测试就必须起服务、造 HTTP，速度慢且难定位
- **085 REST API 设计、OpenAPI 与幂等**：用 POST 承担所有操作、或不给写接口加幂等键，网络重试就会重复扣款、重复下单
- **086 WebSocket / SSE / 长轮询与实时推送**：把连接状态只存在单机内存里，扩容后用户重连到另一台实例就会丢消息
- **087 SQLAlchemy、连接池、事务与迁移**：在循环里逐条查询关联对象（N+1），数据一多响应会呈线性劣化，而本地测试集太小看不出来
- **088 Redis 缓存：穿透、击穿、雪崩与分布式锁**：用 SETNX 加过期时间做锁却不在 finally 里比对随机值再删，可能误删别人的锁
- **089 消息队列：Celery / RabbitMQ / Kafka**：把任务体里塞大对象、或消费失败就无限重试，会拖垮队列并阻塞后续消息
- **090 认证授权：Session、JWT、OAuth2 与 RBAC**：把权限判断只写在前端、或用 MD5 存密码，都是会直接导致越权与拖库后果的错误
- **091 文件、对象存储、搜索与 gRPC**：把上传文件直接写本地磁盘，容器重启即丢，扩容后另一实例也读不到
- **092 阶段综合：生产级短链服务**：把 301 与 302 混用，会让统计口径与 SEO 行为都不受控；不做限流则会被刷接口打满发号器

### 阶段九 · 数据科学与 AI 工程

- **093 NumPy 向量化、广播与内存布局**：用 arr[arr > 0] 返回的副本做赋值，改动不会落回原数组，这类静默失败很难查
- **094 Pandas 清洗、分组、透视与时间序列**：用 inplace 链式操作、或在循环里逐行 iterrows，既慢又容易产生 SettingWithCopy 警告下的静默错误
- **095 可视化：Matplotlib / Seaborn / Plotly 与图表选型**：截断纵轴、双轴叠加、用 3D 饼图展示占比，都会把微小差异放大成显著结论
- **096 统计基础：分布、检验与相关性**：反复检验直到 p 值显著、或把相关性当因果写进结论，是数据报告里最常见的两类错误
- **097 机器学习流程：特征、划分与评价**：只用准确率评价极不平衡的数据集，全预测多数类就能拿到 99 分
- **098 经典算法：KNN、线性与逻辑回归**：不做特征缩放就跑 KNN 或梯度下降，量纲大的特征会主导结果，收敛也会变慢
- **099 SVM、核方法、决策树与随机森林**：不限制树深又不做交叉验证，训练集必然满分而线上表现很差
- **100 集成学习：Boosting、XGBoost 与 LightGBM**：在大规模特征上不做缺失与类别处理直接训练，训练时间与内存都会失控
- **101 无监督学习：KMeans、DBSCAN、PCA 与异常检测**：把 PCA 主成分当成有明确物理含义的因子，或在高维稀疏数据上直接算欧氏距离，结论往往站不住
- **102 模型调优：交叉验证、正则化与过拟合**：在测试集上反复调参，等于把测试集变成验证集，最终报告的分数毫无意义
- **103 深度学习与 PyTorch：张量、自动微分与训练循环**：忘记 zero_grad、或验证阶段没关梯度，会出现梯度累积与显存悄悄涨满
- **104 LLM 应用工程：Prompt、RAG、Agent 与成本**：把检索到的片段无脑塞进上下文、或让 Agent 无上限循环调用工具，会同时推高成本与失控概率

### 阶段十 · 分布式与云原生

- **105 CAP / BASE 与一致性模型**：把「最终一致」当成「不用管一致性」，用户支付后立即查不到订单，客服工单就会爆
- **106 幂等、分布式锁与限流**：用「先查后写」实现幂等，并发下依旧会重复；锁不设租约则持有者崩溃后永久阻塞
- **107 分布式事务：2PC / TCC / Saga / 消息最终一致**：Saga 的补偿操作本身也可能失败，只写正向流程等于把不一致留到线上
- **108 分布式 ID、一致性哈希与分片**：用随机 ID 做分片却按时间范围查询，会变成全片扫描；时钟回拨还可能让雪花 ID 重复
- **109 Raft 共识、服务发现与配置中心**：把配置中心当数据库频繁读写，或让服务发现承担健康判断的全部责任，都会在故障时放大影响
- **110 容器化与 Kubernetes 部署**：不设内存限制，CPython 的缓存与第三方库会让容器反复被 OOMKill；探针写成强依赖数据库则一抖动就全量重启
- **111 GitOps、灰度发布与可观测平台**：只做全量滚动更新、又没有与指标联动的回滚条件，故障会等比放大到全部实例
- **112 任务调度、SRE 与混沌工程**：把告警阈值设成「CPU 高」而不是「用户请求失败率」，值班会被噪声淹没却漏掉真实故障
- **113 安全工程：依赖、注入、序列化与密钥**：依赖不锁版本、镜像里留 .env、日志里打印 token，等于把入口写进交付物

### 阶段十一 · 资深进阶与源码

- **114 CPython 源码：对象、帧与求值循环**：只看博客结论不看版本，CPython 3.11 之后的自适应特化会让很多旧文章完全失效
- **115 内存分配器 pymalloc 与 GC 源码**：看到 RSS 高就断定泄漏、直接调 gc.collect，往往只增加停顿而不解决问题
- **116 导入系统源码与 import hook**：用 import hook 做隐式魔法（自动补丁、远程加载），会让依赖分析和安全审计彻底失效
- **117 asyncio 事件循环与 Task 源码**：把 CPU 密集循环放进 async 函数不加 await，事件循环会被独占，所有超时与心跳一起失效
- **118 GIL 源码、自适应解释器与无 GIL 路线**：把「无 GIL」当成默认可用的现有能力，或在 C 扩展里假设持有 GIL，都会在自由线程构建下崩溃
- **119 极致优化：从剖析到 C 扩展的十倍案例**：一上来用 C 重写热点，会牺牲可维护性，却可能发现瓶颈其实是一次多余的数据库往返
- **120 架构设计：领域分层、演进与重构**：在没有清晰领域边界时拆微服务，会把一次函数调用变成一次分布式故障
- **121 资深能力图谱、技术选型与持续精进**：追逐每个新框架却不建立评估维度，选型的依据永远只剩热度

### 阶段十二 · 工程实战

- **122 实战 01 · 待办清单 CLI 与命令分发**：直接覆盖写文件，进程中途被杀就会留下半截 JSON，数据永久损坏
- **123 实战 02 · 文件检索、日志与自动化办公**：直接用 os.remove 做清理脚本，路径拼接错一个斜杠就可能删掉目标目录之外的东西
- **124 实战 03 · 邮件、PDF、Excel、Word 与图像视频**：把邮箱授权码写死在脚本里、或用字符串拼 HTML 邮件正文，都会带来凭证泄漏与内容错乱
- **125 实战 04 · Selenium 表单自动化与定时任务**：用 sleep 硬等、或把账号密码写进脚本，既不稳定也不安全
- **126 实战 05 · 短链与图片服务**：把图片二进制存进数据库，备份与查询会一起变慢；不做 Content-Type 校验还会带来存储型风险
- **127 实战 06 · 日志 ETL 与 CSV / SQL 查询工具**：用一次性脚本 read() 全量载入日志，文件稍大就 OOM；失败后从头跑又会重复入库
- **128 实战 07 · 并发爬虫与分布式调度**：没有共享去重集合，多个 worker 会重复抓同一批 URL；节点崩溃后队列里的任务会永久丢失
- **129 实战 08 · KV 贯穿线 ① 内存版与接口抽象**：一开始就把 dict 直接暴露给命令层，后面加网络与持久化时必须重写全部调用点
- **130 实战 09 · KV 贯穿线 ② 协议帧与网络层**：用换行分隔却允许值里出现换行，协议立刻失效；不做长度上限还会被单条超大请求打满内存
- **131 实战 10 · KV 贯穿线 ③ WAL、持久化与并发控制**：每次写都 fsync 保证最强一致但吞吐很低，完全不刷盘又可能在断电时丢一批已返回成功的请求
- **132 实战 11 · 分片复制、AI 网关与能力收束**：只做分片不做副本，节点一挂就是永久丢数据；流式接口不设超时与预算上限则会被长连接拖垮
