## 1. 先建立直觉

**目录重构**。这里的关键词是「什么时候」和「代价是什么」。Python 的机制大多不是非黑即白的开关，而是在可读性、性能与灵活性之间做的取舍。把取舍写清楚，遇到新版本或新框架时才能自己推导，而不是重新背一遍结论。

**依赖锁定**。从实现角度看，这一层的行为最终会落到对象协议、字节码或运行时状态上。理解底层并不意味着每次都要写底层代码，而是当现象与直觉不符时，你知道该用 dis、inspect、tracemalloc 还是 cProfile 去验证，从而把猜测变成证据。

**类型与规范**。工程里最容易出问题的不是不会用，而是用在错误的边界上：数据规模变大、并发进入、依赖升级、跨平台部署之后，原本成立的假设会逐个失效。因此本讲同时给出适用条件、失效信号和一条可回退的路径。

## 2. 语法与规则：把行为跑出来

### 2.1 主示例

**目录重构**。从实现角度看，这一层的行为最终会落到对象协议、字节码或运行时状态上。理解底层并不意味着每次都要写底层代码，而是当现象与直觉不符时，你知道该用 dis、inspect、tracemalloc 还是 cProfile 去验证，从而把猜测变成证据。

```python
import subprocess, sys
checks = [
    [sys.executable, "-m", "compileall", "-q", "src"],
    [sys.executable, "-c", "print('lint ok')"],
]
for cmd in checks:
    r = subprocess.run(cmd, capture_output=True, text=True)
    print(r.returncode, r.stdout.strip() or "ok")
```

### 用命令行复现

本机不用起服务，一条命令就能把本讲的关键行为再验证一次：

```bash
python -m compileall -q . && python -m pytest -q
```

把命令里的输入换成你自己的数据，观察输出是否仍符合 **目录重构** 的规则；若结果不一致，先核对 Python 版本与依赖版本，再回到主示例逐行定位差异。这条命令也可以直接加进 CI，作为本讲结论的回归检查。
